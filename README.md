## Задача в двух предложениях

Уходящий абонент — тот, кто расторг договор (`termination`) в календарном месяце, начинающемся на дату расчёта T (1-е число, 00:00 МСК). На каждую T решение ранжирует всю активную базу по риску расторжения. Заказчик получает список контактов для удерживающей кампании: не более 10% активной базы, то есть K = floor(0,10 × N).

## Короткий протокол — заполнен до test

Протокол заполнен и закоммичен **до** расчёта на test: коммит «Протокол итоговой проверки до расчёта на test», файл [`docs/06_protocol.md`](docs/06_protocol.md).

| Test и исход | T = 01.09.2026; метка — расторжение в `[01.09.2026, 01.10.2026)`; все исходы наблюдаемы |
| Правило сравнения | Одна активная база; K = floor(0,10 × N); равные score — по `customer_id` по возрастанию. Baseline — долг на конец прошлого месяца (`debt_prev_rub`) по убыванию; неизвестный долг — после всех известных (на validation и test таких строк нет) |
| Метрики | Recall@K, Precision@K, N, K, найдено / ушли |
| Использовали test для выбора? | **Нет.** Test не загружался на этапе 5; модель оценена один раз, без fit и без нового выбора |

## Как запустить

- **Входы:** признаки этапа 4 `data/features/features.csv`, `labels.csv`, `split.csv` и сохранённая модель этапа 5 `models/stage5_candidate.joblib`.
- **Начало расчёта:** итоговая проверка начинается от подготовленных признаков этапа 4. Полная цепочка от исходников тоже воспроизводится (см. ниже).
- **Среда:** Python 3.10+ (проверено на 3.13.15).

  ```bash
  python -m venv .venv
  ```

  ```bash
  .venv\Scripts\python -m pip install -r requirements.txt
  ```

  Зависимости: pandas 3.1.0, numpy 2.5.4, scikit-learn 1.9.1, joblib 1.6.0, matplotlib 3.11.2, pytest 9.1.1. В Linux/macOS вместо `.venv\Scripts\` — `.venv/bin/`.

- **Итоговая проверка:**

  ```bash
  .venv\Scripts\python -m src.stage6
  ```

  Повторный запуск той же модели со сверкой:

  ```bash
  .venv\Scripts\python -m src.stage6 --verify
  ```

  - `final_metrics.csv` — таблица качества;

## Результаты

| Период | Подход | N / K | Найдено / ушли | Recall@K | Precision@K |
|---|---|---|---|---|---|
| Validation (01.08.2026) | Baseline (долг) | 1 929 / 192 | 14 / 63 | 22,2% | 7,3% |
| Validation (01.08.2026) | Модель exp03 | 1 929 / 192 | 19 / 63 | 30,2% | 9,9% |
| Test (01.09.2026) | Baseline (долг) | 1 916 / 191 | **30 / 65** | **46,2%** | **15,7%** |
| Test (01.09.2026) | Модель exp03 | 1 916 / 191 | 26 / 65 | 40,0% | 13,6% |

**Вывод.** На validation модель нашла на 5 уходов больше правила долга, но на test преимущество не сохранилось: при том же K = 191 модель нашла 26 уходов, правило — 30 (на 4 больше). Это согласуется с временными фолдами этапа 5, где правило тоже было лучше в среднем (74 против 70 из 180). Списки модели и правила совпадают на 147 из 191 абонентов. Оба нашли одних и тех же 24 ушедших; только модель — ещё 2, только правило — ещё 6.

## Небольшой анализ

**Сегментное сравнение: долг на конец прошлого месяца** ([`test_segment_debt.csv`](reports/stage6/test_segment_debt.csv)). Попадание считается в общий top-K, новые 10% внутри групп не отбираются.

| Группа (test) | N | Ушли | Выбрано в top-K: модель / baseline | Найдено: модель | Найдено: baseline |
|---|---:|---:|---|---|---|
| Долг > 0 | 426 | 40 | 191 / 191 | 26 из 40 | 30 из 40 |
| Долг = 0 | 1 490 | 25 | 0 / 0 | 0 из 25 | 0 из 25 |

Обе стратегии отбирают всех 191 абонентов из группы с долгом: должников 426, а это больше K. Поэтому **25 из 65 ушедших (38%), у которых долга не было, при лимите 10% не находит ни один подход**. Модель отличается от правила только порядком внутри должников, и на test этот порядок оказался хуже. Чтобы находить уходы без долга, нужен отдельный сигнал — это направление для следующего исследования.

Сегмент выбран после просмотра test. Первоначально запланированный разбор по стажу малоинформативен: в группе со стажем < 90 дней на test всего 1 уход (0 из 1 найдено у обоих подходов). Сами прогнозы, метрики и списки контактов от смены разбора не менялись.

**Три признака** — коэффициенты модели взяты на стандартизованной шкале ([`model_coefficients.csv`](reports/stage6/model_coefficients.csv)):

| Признак | Что измеряет и почему может быть связан с уходом | Основание: EDA / уже полученные коэффициенты |
|---|---|---|
| `payment_delay_prev_days` | Задержка оплаты в прошлом месяце, в днях. Абонент, переставший платить, мог уже решить уйти или испытывать финансовые трудности | EDA (этап 3): без оплаты (28–31 дн.) отток 10,6% против 1,4% при своевременной. Коэффициент модели +0,41 — самый большой среди признаков платежей |
| `debt_months_3m` | Число месяцев с долгом за последние 3. Устойчивый долг отличает систематическую неоплату от разовой задержки | Train (этап 4): 0 мес. — 1,2% ухода, 3 мес. — 11,4%. Коэффициент +0,23 |
| `traffic_prev_gb` | Трафик за прошлый месяц, ГБ. Снижение использования может предшествовать уходу: абонент переходит к другому оператору | EDA: медиана у ушедших 21,7 ГБ против 23,1 ГБ. Коэффициент −0,24 — больше трафика, ниже риск |

Связь в данных не доказывает причину ухода. Выводы EDA сами по себе не доказывают важность признака для модели. Коэффициенты отражают вклад при остальных признаках модели и искажаются из-за корреляции признаков долга и оплаты.

## Вывод и ограничения

**Результат.** На отложенном сентябре правило «сортировка по долгу прошлого месяца» нашло 30 из 65 уходов (Recall@10% 46,2%, Precision 15,7%). Модель нашла 26 (40,0%, 13,6%). Модель не превзошла baseline.

**Рекомендация.** Для ближайших кампаний использовать правило по долгу: оно не требует обучения, прозрачно и было не хуже модели на test и на трёх месяцах внутри train. Модель не внедрять. Её стоит сравнивать с правилом на каждом новом месяце и отдельно исследовать сигнал для 38% уходящих без долга. Эффект удерживающего контакта проверить пилотом с контрольной группой.

**Два главных ограничения:**

1. **Короткая проверка во времени.** Один test-месяц с 65 уходами: разница в 4 найденных абонента — это 6 п.п. Recall. Validation и test дали противоположный знак разницы, поэтому устойчивость ни одного из подходов не доказана.
2. **Риск — не эффект.** Риск ухода не показывает, сколько уходов предотвратит контакт. Исторические метки не отражают удерживающую кампанию, а денежный эффект без данных о стоимости контакта и ценности абонента не оценивался.

**Повторный запуск** (11.11.2026, та же модель и те же входы): списки контактов validation и test, ранги и метрики совпали (`python -m src.stage6 --verify`, `repeat_check.json`). Также проверено:

- у модели и baseline одна база и одинаковые N и K;
- модель загружена без fit, SHA-256 файла модели не изменился после расчёта;
- test не использовался для выбора.
